# Porting 0.9.7

The Python reference moves from `600b10e7e159` (0.9.6) to **`5b973a65ab58`**
(`5b973a65ab583082069afaa67e2baf7257cbc4950a89460c9912851821258d16`). Two files
change, both under the existing `runtime` capability: `src/thalovant/intents.py`
and `src/thalovant/events.py`. No vector file changes and no new capability, so
a port acknowledges the digest and ports the behaviour below.

## Why

Two things kept "What you can say" from being useful, and both were measured
on all 13 public hubs on 2026-10-11.

**A phone in a language the hub did not load saw an empty list.** A hub loads
its `lang` and `secondary_langs` (en-US and fr-FR on most public hubs, plus
de-DE on Story Time) and its manifest lists nothing under any other tag. A
phone set to es-ES, ja-JP, or de-DE on most hubs asked `ovos.intent.list
{lang}` and got zero rows. The usual-form retry also got zero rows, so the
phone showed nothing at all. The hub still answers that person, in its own
language.

**Skills with no intents never showed up.** `ovos.skills.fallback.list`
came from ovos-core #951, and #988 reverted it the same day (456981c6a3). No
hub answers it. Every SDK therefore reported fallbacks as unknown, and a skill
that registers no intents vanished from the list. Daily Desk's
`thalovant-skill-memory` (capabilities fallback and converse, 0 intents) and
Ops Copilot's `custos-fallback` are two examples. The revert points at
`ovos.skills.list` (OVOS-INTENT-4 §10.3), and that query does work on the
deployed ovos-core 3.7.2a2.

## 1. List in the hub's language when the asked one has nothing

The inventory already asks the language and then its usual form. When both
leave the language without an enabled template row, and `nearest` is on (the
default), ask once more:

```
ovos.intent.list  {"include_definitions": true}   <- no "lang" key at all
```

Send `include_definitions` only when describing is on, exactly as for the
per-language listing. Leave `lang` out of the request context too. The reply
lists every language the hub loaded. On Rewrite Forge that is
`{fr-FR template: 70, en-US template: 70}`.

- Group the rows by their `lang` (hub spelling, e.g. `en-US`). Treat
  `fr-fr` and `fr-FR` as one group, keep the first spelling seen, and keep
  the hub's order.
- Ask it **at most once per inventory call**, lazily: only when some asked
  language still has no template row after the usual-form step. A language
  with a template row never triggers it.
- Choose with `nearest_hub_language(asked, groups, hub_lang)`:
  1. Candidates are the groups with at least one enabled `template` row. If
     there are none, return nothing.
  2. Use the same language first: `closest_lang(asked, candidates)` with the
     default distance, so `en-CA` takes `en-GB` when the hub loaded no
     `en-US`.
  3. Then use the hub's own language: `closest_lang(hub_lang, candidates)`,
     where `hub_lang` is `context.session.lang` on **the reply** to the
     language-less listing. A request that names no language is answered in a
     session the hub opened in its default language. On Daily Desk that is
     `en-US`, even though the hub lists `fr-FR` first. Treat it as a hint:
     if it names nothing the hub listed, skip it.
  4. Otherwise take the candidate with the most enabled template rows. On a
     tie, take the first one listed.
- If a choice is made, those rows become the language's listing and the
  chosen tag becomes its `listed_in` entry. If the asked language had keyword
  rows, it keeps them only when nothing better exists. Template rows are
  never traded for fewer.
- A timeout, a `hive.policy.denied`, or `ok: false` on this query leaves the
  result exactly as it was before the query. It never raises.
- Two asked languages that land on the same hub language share one key. If
  `en-us` was asked and `ja-JP` picked `en-US`, the phrases stay under
  `en-us` only, never split between `en-us` and `en-US`.
- Describing: rows without a definition are described under the chosen tag,
  as before.

`listed_in` already exists in every port. It now differs from `languages`
whenever this step picked a language. Callers that show sentences should say
which language they are in when that is not the person's language.

The serialised inventory (`as_dict` / the port's equivalent) gains
`listed_in`.

## 2. Fallback skills from `ovos.skills.list`

Replace the `ovos.skills.fallback.list` probe with:

```
ovos.skills.list {}  ->  ovos.skills.list.response
  {"ok": true, "skills": [{"skill_id", "session_id",
                           "capabilities": ["fallback", "converse"],
                           "intents": 16}, ...]}
```

- A fallback is a row whose `capabilities` list contains `"fallback"`.
- Keep a row only when its `session_id` is absent, empty, or `"default"`.
  Every installed skill loads in `default`, and a row from another session
  belongs to somebody else.
- Skip a malformed row (no string `skill_id`, `capabilities` not a list)
  and keep the rest.
- Sort by skill id and de-duplicate.
- The probe keeps its 1.5 s cap (`min(timeout, 1.5)`) and its semantics.
  Unknown (`None` / `fallbacks_known = false`) means a timeout, a denial,
  `ok: false`, or `skills` not being a list. A known empty list means the
  hub said there are none.
- **Stop asking `ovos.skills.fallback.list`.** No hub answers it, so every
  inventory call was spending the full 1.5 s on it. Keep the event-name
  constants so that nothing exported disappears.
- **Priority is not served.** `ovos.skills.list` has no order field and the
  query that had one was reverted. `HubFallback.priority` becomes optional
  and is always `None`/absent. Do not invent one. Document that the list is
  in skill-id order and does not say who is tried first.

## Connections must be allowed to ask

`ovos.skills.list` has to be on a connection's allow-list like every other
query. thalovant-api grants it to every connection (see the API change that
adds it beside `ovos.skills.fallback.list`). Until a connection is granted it,
the hub answers `hive.policy.denied` and fallbacks stay unknown, which is
the same as today.

## Tests a port should carry

Use the Python suite (`tests/test_intents.py`, "A language the hub never
loaded" and the fallback section) as the checklist:

- es-ES, ja-JP, and de-DE phones on an en-US + fr-FR hub list in `en-US`
  when the reply session says `en-US`, even though French is listed first.
- `en-CA` on a hub with `en-GB` and `fr-FR` picks `en-GB`.
- With no hint, most template rows wins, and a tie goes to the first listed.
- A language the hub loaded never asks the language-less listing.
- A silent, refused, or denied language-less listing leaves the keyword
  rows and `listed_in` as asked.
- `nearest = false` never asks it.
- `ovos.skills.list` filtering covers another session, a non-fallback skill,
  a missing session, and malformed rows. `ok: false` means unknown, and a
  denial means unknown.
- `ovos.skills.fallback.list` is never sent.
