## What changed in the contract

**Vectors.** 31 new cases, and none of the existing ones changed:

| File | Cases | New | What the new cases hold |
|---|---|---|---|
| `api-error-vectors.json` | 13 → 15 | 2 | an echoed validation `input` is never repeated in a message, whatever its key (a bare string under FastAPI's `detail[]`, a list under an ordinary key in `errors[]`) |
| `device-login-vectors.json` | 13 → 20 | 7 | `client_id` sent; `client_id: null` left out; an unknown app (400 `unknown_client`, with the api-errors fields); `describe` read as verified, as unverified, and a 404; a token answer whose body is not a JSON object (`status: null`). New top-level key `home_assistant_client_id` |
| `home-link-vectors.json` | 30 → 35 | 5 | three `speech` cases on the White_Space trim edge; two `queued` cases (a reply withdrawn while it waits behind another frame, and one that goes out) |
| `link-keeping-vectors.json` | 29 → 36 | 7 | three `close` cases with `after_authenticated_frame`; `handshake` situations `client_key_changed`, `client_key_changed_pinned_here`, `closed_after_first_frame`; one `supervise` case for `client_key_rejected` |
| `link-carrier-vectors.json` | new | 10 | KK then XX over HTTPS polling (6) and MQTT (4) |

**Capabilities.**

- `device-login`, `home-link`: the new behaviour, below.
- `binary`: now lists `src/thalovant/_wire.py`. A compressed part of a WIRE-1 frame
  inflates to at most 32 MiB; beyond that, or truncated, the frame is refused.
- `identity`: now lists `src/thalovant/_noise_runtime.py`, for the key-folder rule.
- `link-carriers` (**new**):
  - required: Node, Go and Rust;
  - not applicable, with a reason:
    - Kotlin, Swift and .NET offer only the WebSocket;
    - embedded-c's caller owns every carrier;
    - MCP's carriers are the Node SDK's.

  Every consumer must declare it, either way.

**New behaviour** (the brief has the full rules):

1. **Device login.**
   - `client_id` on begin: send it when given, and leave it out when not. Home Assistant's
     id is `thalovant-home-assistant`.
   - `describe(user_code)`: `GET /v1/auth/device/codes/{user_code}`. It returns `scopes`,
     `client_name`, `client_id`, `client_verified` and `device_name`.
2. **The authenticated-frame rule** (Kotlin's, now everyone's). A close with 1000, 1005 or
   1008 inside the 750 ms window is a refusal only while the hub has sent nothing that
   decrypts under the new session's keys. Any decrypted frame counts: JSON, WIRE-1
   binary, a chunk, or the hub's encrypted HELLO.
3. **`client_key_rejected`.**
   - **What it is:** a refusal as an XX handshake ends, with nothing from the hub in
     between, means the hub pinned another client key.
     - The error is still a refusal in your error model, but its own kind.
     - It names the folder this client's key is in, and the likely other folder.
     - It says "re-pair, or share the key folder".
   - **After KK:** the same close is a plain refusal.
   - **The supervisor:** gives up at once, with reason `client_key_rejected`.
   - **Over HTTPS:** a 401/403 while the client sends the last XX frames, or right after,
     is the same verdict.
4. **Key folder** (no vector: the paths are platform paths).
   - **The rule:** an identity read from a file, with no key folder named, keeps its key
     in a folder tied to that file.
   - **Migration:** the first time that folder is used, copy (never move) the key and hub
     pins from the SDK's previous default, but only when they have met this identity's hub.
   - **Order:** write the pins first and the key last, and skip the copy only when the
     new folder already holds a key. A copy cut short then leaves no key and is made again,
     never the old key without the pin that checks its hub.
5. **Binary frames:** cap zlib inflation at 32 MiB, and refuse a truncated stream.
6. **A reply withdrawn while queued:**
   - the wait for the send path is cancellable;
   - a frame already being written is finished;
   - the link stays as it was.

   This is 0.9.0 behaviour; the `queued` vectors now check it.

**Acknowledging.** For each SDK:

1. Re-vendor the four changed files, plus `link-carrier-vectors.json` where it applies.
2. Implement the items below, then re-run the suite with

## Keep it non-breaking

Owner bar: zero breaking changes, even where 0.x semver allows them. Four of this round's
additions are breaking by default in some languages:

| Addition | Breaks in | Do instead |
|---|---|---|
| a parameter on an existing method | Go (method type), .NET (binary), Kotlin (JVM signature; Java callers), Rust (pub fn) | an overload, or a new method: `BeginDeviceLoginWithOptions`, `begin_device_login_as`, a hidden deprecated overload for Kotlin |
| a field on a pub struct or data class with a public constructor | Rust (struct literal), Kotlin data class (constructor, `componentN`) | a builder, a new options type, or a secondary constructor that keeps the old one |
| a case on a public enum used in `switch`/`when`/`match` | Rust (unless `#[non_exhaustive]`), Kotlin, Swift | Add the case only where the enum is already non-exhaustive or internal. Otherwise keep the refusal case and carry the kind beside it (a flag, a `reason`, an `is_client_key_rejected()` classifier), and name the choice in the PR. |
| a new error type | nowhere, if it extends the refusal type existing code catches | subclass the refusal, or add a classifier (Go `errors.Is`, Rust `is_*()`) |

The supervisor vector records only the outcome name and the decision. How your harness
feeds `client_key_rejected` to the supervisor is up to you; `run()` must still give up on
it at once.
