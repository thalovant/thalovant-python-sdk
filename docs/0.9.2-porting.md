# Porting 0.9.2

The Python reference moves from `3b0acf7c8b2f` (0.9.1) to **`841f3bbeec23`**
(`841f3bbeec23f04c5decae75c9cfd6ea6a397992c7e4d7cd4195dc9dd919cd1a`). Unlike 0.9.1, this
round touches one file and one capability: `src/thalovant/models.py`, under the existing
`runtime` capability (no new capability, no new scope declarations needed).

**Revision note.** This doc originally named the digest `50d65c1596a9…`. Before any port
merged, CodeRabbit caught a real bug on the embedded-C and Node ports (and noted the same
gap in Kotlin's review summary): the assertion check scanned *every* collected event for
`data.meta.thalovant_claimed`, not only the skill's own speak event, so a correlated event
this reply happened to carry — `ovos.utterance.handled`, say — with that same meta shape
would wrongly assert a claim too. The reference moved again, to `841f3bbeec23…`, to fix it.
If you vendored anything against `50d65c1596a9…`, re-vendor against this digest instead.

## What changed

**The bug.** `ThalovantReply.claimed` (formerly: any reply whose pipeline stage names
lack `"fallback"` counts as claimed) cannot separate a skill that deliberately answered
from a fallback tier from the fleet's own generic "nothing matched" catch-all skill: OVOS
puts both in the same `FallbackRange(90, 101)` band, so `pipeline_id` alone never tells
them apart. Seen live: `thalovant-skill-home` genuinely turned a light off from the
fallback tier; a satellite listening without a wake word read the reply as unclaimed
and stayed silent.

**The fix.** An opt-in, additive signal. A skill's own `speak` event may carry
`data["meta"] = {"thalovant_claimed": True, ...}` — thalovant-skillkit's `speak_to`/
`emit_speech` already builds `meta = {**(meta or {}), "skill": skill_id}` onto every
`speak` message, so a skill passing `meta={"thalovant_claimed": True}` to that call is
already something every SDK's event collection sees. `claimed` now checks for a `True`
value under that key first, before falling back to the existing pipeline-tier heuristic —
**but only on the skill's own speak event** (`EVENT_SPEAK`/`EVENT_OVOS_UTTERANCE_SPEAK`),
never on any other collected event this reply happens to carry. It is checked after the
`ok` guard returns early, so it can never rescue a reply where `ok` is `False` (unhandled,
or carrying a `failure_event`). Any other value under the key — `False`, a string, an int,
or the key simply absent — is inert.

```python
THALOVANT_CLAIMED_META_KEY = "thalovant_claimed"

@property
def claimed(self) -> bool:
    if not self.ok:
        return False
    if self._has_asserted_claim():
        return True
    stages = self.pipeline_ids
    if not stages:
        return True
    return any(FALLBACK_PIPELINE_MARK not in stage for stage in stages)

def _has_asserted_claim(self) -> bool:
    return any(
        event.name in (EVENT_SPEAK, EVENT_OVOS_UTTERANCE_SPEAK)
        and isinstance(event.data.get("meta"), dict)
        and event.data["meta"].get(THALOVANT_CLAIMED_META_KEY) is True
        for event in self.events
    )
```

Scoping to speak events matters because `self.events` is every event this reply
collected — not only speak: `ovos.utterance.handled` and others land in it too, and a
consumer that scans all of them accepts an assertion from any of them. `media_events`
(the wider `MEDIA_EVENTS`, which also includes a skill sound clip with no meaning as a
claim) is the wrong set to filter by here too — use exactly these two event names.

**Vectors.** `reply-claim-vectors.json` gains a `metas` array and a `names` array, both
parallel to the existing `contexts` array (one entry per event; a `null` meta means that
event carries no `meta` at all, and an absent/`null` `names` entry means that event is
named `"speak"` — both match every pre-0.9.2 case unchanged) and 8 new cases:
`fallback-claim-asserted` (the `thalovant-skill-home` shape),
`fallback-generic-catch-all-unasserted` (the regression case: a real fallback-tier
`skill_id`, no assertion, still `claimed: false`), `fallback-claim-false-is-inert`,
`fallback-claim-non-bool-is-inert`, `fallback-claim-on-second-event-still-counts`,
`assertion-cannot-rescue-a-failed-reply`, `assertion-on-an-intent-reply-is-a-no-op`,
`assertion-on-a-non-speak-event-is-ignored` (the CodeRabbit regression case: the same
meta shape on a correlated `ovos.utterance.handled` event must not assert a claim). No
existing case's `contexts` or `expected` changed.

**If your port already vendored the first cut of these vectors** (before this revision),
re-vendor: `names` is new, and the checker/harness that builds events from `contexts` must
now also read the parallel `names` array (defaulting every entry to `"speak"` when the
array is absent, exactly as before) instead of hardcoding every event's name to `"speak"`.

## Acknowledging

For each SDK:

1. Locate this SDK's `ThalovantReply`-equivalent and the `claimed`-equivalent
   check — every SDK already collects `speak`-type events with a `.data`/`meta` (or
   equivalent) accessor for `pipeline_ids`/`skill_ids`; reuse it rather than adding a new
   event-collection path.
2. Add the same constant, spelled in the SDK's own naming convention (e.g.
   `ThalovantClaimedMetaKey` in Go/.NET/Swift PascalCase-adjacent conventions,
   `THALOVANT_CLAIMED_META_KEY`/`thalovantClaimedMetaKey` elsewhere — match how
   `FALLBACK_PIPELINE_MARK`'s equivalent, or the nearest existing public constant, is
   already spelled in that SDK), and export it wherever `claimed`/`pipelineIds`/
   `skillIds` are already exported.
3. Re-vendor `reply-claim-vectors.json` and extend the harness that reads `contexts` to
   also read the parallel `metas` and `names` arrays when present (a harness written
   before this round has neither and must gain both; this is the one non-mechanical part
   of the port). `names` defaults every entry to `"speak"` when the array is absent.
4. Re-run the suite with `THALOVANT_CONFORMANCE_OUT=contracts/conformance-results.json`
   (or the equivalent env var already used for that SDK's `reply-claim` recording, if it
   records this vector at all — most consumers only ever assert against it inline, matching
   how `runtime` has worked since 0.9.0; recording is optional here exactly as it was
   before this round).
5. Append `841f3bbeec23…` to `reference_digests`. No capability re-declaration is needed:
   `runtime` already lists `src/thalovant/models.py` and every consumer already carries it
   as `required`.

Python merges first, as always; each port's own parity check reads Python's `main`, and a
port that vendors the new vectors fails against the old ones committed there.

## Keep it non-breaking

This round adds one module-level constant and changes the internal ordering of one
read-only property's logic; it adds no parameter, no field on a public type, and no new
enum case, so none of 0.9.1's four breaking-by-default shapes apply here. The only per-SDK
judgment call is the constant's exported spelling, and matching the file's own convention
for other similarly-scoped public string constants is enough.
